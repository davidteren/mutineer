Your tests pass. Would they catch a bug?

Mutineer makes small changes to your Ruby code, then runs your tests. If they still pass, it shows you the change they missed. This is called mutation testing.

How it works

Find a bug your tests would miss.

Each changed version of your code is called a mutant. For example, a discount should start at 10 items. Tests for 1 and 50 items can pass even when the rule is wrong at exactly 10.

Line coverage tells you which lines ran. Mutation testing checks whether your tests notice a change to those lines.

Change one thing

Mutineer changes a comparison, swaps an operator, or removes a statement. Each change must still be valid Ruby before Mutineer tests it.

Run your tests

Mutineer runs the tests that cover the changed line. A test should fail when the change breaks a rule your code must follow.

Read what they missed

Killed means a test caught the change. Survived means the tests still passed. Read the changed line and add a test if it exposes a gap. Some changes leave the behaviour the same; record why you ignore those.

Reading a result24 caught. 1 missed.

96% mutation score. 24 killed ÷ (24 killed + 1 survived). Uncovered and unscored changes are excluded. The score does not prove that the code has no bugs.

Your first run

Start with one file.

Use Ruby 3.4 or later on Linux or macOS. Choose a small file with tests that already pass. Mutation testing runs tests repeatedly, so it takes longer than a normal test run.

Install Mutineer

$ gem install mutineer

In a Bundler project, add gem "mutineer", group: :test to your Gemfile, run bundle install, and prefix the commands below with bundle exec.

Run it against your file and its test

$ mutineer run lib/discount.rb \ --test test/discount_test.rb

Replace both paths with files in your project. For RSpec, use a spec file with --test. For Rails, follow the one-model guide.

Read one surviving change

Find Surviving Mutants in the report. Read the changed line. Add a test that passes with the original code and fails with the change, then run Mutineer again.

Some changes have the same result as the original. Those are called equivalent mutants. Review them and record a reason before you ignore them.

No file in mind? Run the complete example →

You do not need a score target for your first run. After you understand the results, add a CI check or save settings with mutineer init (1.7+).

AI agents & CI

Give your pipeline evidence.

Once you understand your first report, use Mutineer to check code changes in CI or give an AI coding agent a specific test gap to fix. JSON reports describe each missed change. You can limit runs to changed lines and compare results with an earlier run.

Agent inner loop

Close the loop on test quality

An agent writes code and tests, then runs Mutineer on just the diff. Each survivor ships a ready-made diff to feed back: "write a test that fails under this change." Ask for a human review when a survivor cannot be caught; it may leave the behaviour unchanged.

--since origin/main --format json

PR / CI gate

Fail only when a PR makes tests worse

Diff the run against a stored baseline by mutant id. Exit 1 on any new survivor or a score drop — adopt mutation testing on a legacy suite without fixing everything first.

--baseline prior.json --threshold 90

Why Mutineer

Small tool. Exacting work.

Prism and the standard library provide the runtime. Test-framework changes stay in disposable child processes; Rails apps can use the optional --rails or --boot entry point.

Zero runtime deps

Mutineer uses the parser and standard library included with Ruby 3.4 or later. It adds no runtime gems.

Valid mutants only

Every mutation is re-parsed before it runs. Syntactically broken mutants are skipped, not counted against your score.

Fork isolation

Each mutant runs in a separate process on Linux or macOS. Plain Ruby runs use multiple workers. Rails runs need --daemon for multiple workers. --test-command forces one Mutineer worker. It also sets PARALLEL_WORKERS=1 for Rails tests. A script that sets this variable again can start Rails test workers.

Coverage-mapped

A per-mutant coverage map runs only the test files that reach the mutated line. Digest-keyed cache skips unchanged work.

CI & agent ready

Stable, sorted --format json with a versioned schema and mutant ids that survive unrelated edits. --threshold and --baseline gate the build.

Rails-aware

Use --rails to load your app. Minitest apps can add --daemon for worker test databases on SQLite files, PostgreSQL, or MySQL 8. Start with one model.

Operators

Twenty-one ways to break your code.

Five run by default. Sixteen Tier-2 operators are off until you ask for them with --operators or .mutineer.yml — they're noisier, but they catch deeper gaps.

Mutineer and Mutant

Written from scratch. MIT licensed.

Mutineer was written from scratch. It contains no code from Mutant or any other mutation-testing tool. Mutineer’s own code is licensed under MIT.

Mutant is the established tool, with a deeper operator set. Mutineer trades that depth for an MIT license, no dependencies, and a JSON contract for CI and agents.
