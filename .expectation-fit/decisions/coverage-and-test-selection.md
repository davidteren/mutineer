# Coverage and test selection

- **Document --coverage-from Scope and Checks.** When documenting `--coverage-from`, first state that the flag applies only to in-process `--rails` or `--boot` runs and that other run modes ignore it. Then describe the clean check for those in-process runs: only the test files that cover a source line run alone and together, and every test file runs when none covers a source line; a red test outside that set does not stop the run; and Mutineer prints the number of files it did not check. (cubic `874ff78b`, updated 2026-11-16)
- **Coverage Map Rebuild Triggers.** When reviewing documentation of Mutineer's coverage map cache, verify that it says changes to a source, a test, or a project file loaded by the tests rebuild the map. (cubic `4b6099c5`)
- **Retry Failed Captures on Cache Hits.** On a coverage cache hit, retry every test file whose last capture failed, even if it is not known to cover a source line, because its coverage is unknown. (cubic `33179fbf`)
- **Validate Reused Coverage Captures.** Before reusing a `--coverage-from` capture, validate every entry the reuse path reads against the types written by `save`; reject mismatches with exit 2 and a reason, while retaining the missing-fingerprints message when keys are absent entirely. Also include the effective Minitest seed in the coverage-cache digest, and reject reuse of a capture or saved `--coverage-from` capture made with a different effective seed (leading to a different test order), naming the seed change as the reason. (cubic `c37fcc5e`)
- **Digest Project RSpec Options.** When reviewing RSpec coverage-digest inputs, verify that project `.rspec` and `.rspec-local` files are included so changes to their options invalidate the digest. Not when: Do not apply the inclusion rule to `~/.rspec` or to a helper's `config.seed` when that helper is not among the captured project files. (cubic `083fb648`)
- **Select New Mutineer Test Files.** When a Mutineer rerun command explicitly lists tests with `--test`, instruct the agent to add each newly created test file to that selection before reporting `summary.score`. (cubic `0d65ce67`)
- **Explain Test Glob Allowlists.** When documenting a Rails `--test` glob used to skip system tests, state that it selects only the paths it names and tell readers to include every other test directory and each root-level test file they use. (cubic `022dac07`)
- **Tests Map Exit-Code Documentation.** When documenting `.mutineer.yml` `tests:` map exit codes, state that malformed maps exit 2 and unmatched patterns exit 2 only without `--test`, including under `--dry-run`. (cubic `60b93592`)
- **Document Rails worker override for test-command.** When documenting Mutineer custom `--test-command` behavior, state that it forces a single Mutineer worker and sets `PARALLEL_WORKERS=1` for Rails test runs by default. Also state that a `--test-command` script can set `PARALLEL_WORKERS` again to re-enable Rails test workers, so the docs do not imply custom commands always run serially. (cubic `e1dec366`)
- **Timeout mode applicability.** When reviewing the `--timeout` rule, limit its behavior to in-process tests and state that it does not apply to `--daemon` or `--test-command`. (cubic `d4a318b2`)
- **Explicit RSpec Seed-Setting Syntax.** When reviewing RSpec seed-setting guidance (e.g., in docs/cli.md or related docs), verify it spells out the seed mechanisms explicitly: `--seed N` or `--order rand:N` on the command line, in `SPEC_OPTS`, or in `.rspec`, and `config.seed = N` in a spec helper, a `--require` file, or the boot file. Confirm the docs distinguish setting a seed from merely reading the `config.seed` getter (as in `Kernel.srand config.seed`), which does not set one, and tell readers to keep `--order rand` out of `SPEC_OPTS`, which RSpec reads after the command line. (cubic `e3620dc4`)
- **Advertise the Last RSpec Seed.** When `SPEC_OPTS` contains multiple seed-bearing options, verify that `advertised_seed` preserves their order and reports the last option's seed. (cubic `a03d682d`)
- **RSpec SPEC_OPTS Order Precedence.** When reviewing RSpec fixed-order advice, verify that it tells users to keep `--order rand` out of `SPEC_OPTS`, which RSpec reads after the command line. (cubic `8c5900f0`)
- **Last RSpec Order Option Decides the Warning.** In `--test-command` runs, `ExternalBackend.random_order` reads RSpec order options in RSpec's order: `.rspec`, `.rspec-local`, the command, `SPEC_OPTS`. The last `--seed` or `--order` option decides, and the order is fixed only when it is `--seed N` or `--order rand:N`. With `--options` or `-O` in the command, it skips the two files, as RSpec does. RSpec ignores `--options` in `SPEC_OPTS`, so that does not skip them. (#522)
- **Check Runner Seeds Independently.** When `random_order` processes output from a command that runs both Minitest and RSpec, check each runner's seed line independently so a fixed-seed Minitest run does not hide an unseeded RSpec run. (cubic `c4435e08`)
- **Shared seed, distinct file order.** When documenting Mutineer test ordering, or reviewing clean-check and mutant-run behavior, preserve that in-process clean checks and mutant runs share a seed (Mutineer sets no seed for `--test-command`), while a multi-file mutant run may use a different file order. Minitest class order within a file is independent of other files, multi-file mutant runs use coverage order, and the combined clean check uses the supplied test order. (cubic `479305c7`, `3b05bf9e`, updated 2026-11-16)
- **Scope of since_paired_tests.** When documenting or reviewing `since_paired_tests`, state that it is off by default, that it applies to in-process and `--daemon` runs under `--since` whose tests Mutineer paired, that `--test`, `--test-command`, `--baseline` (flag or file key; a narrowed run could hide a new survivor as `no_coverage`, #552 item 3), `--coverage-from` on an in-process `--rails` or `--boot` run (`JobPlan.coverage_from_reused?`) and a dry run keep the full list, that a `--threshold`-only gate can still pass with a survivor hidden that way, and that the source list is not narrowed (`JobPlan.since_tests`). (#496)
