# JSON schema and baseline

- **Sync published contract copies.** When changing Mutineer's JSON schema or CLI contract documentation (fields, options/qualifiers, or `schema_version` examples) in docs/json-schema.md or related contract docs, update every contract copy in the same change. `docs/llms-full.txt` is not a committed copy: `rake site:build` generates it into `_site/` from the docs, so run that build and check the generated file rather than committing one. Ensure all corresponding tables, option rows, qualifiers, and version examples match the current schema and exit-code behavior so the published reference never lags or mixes versions. (cubic `f6bb5e9b`, updated 2026-11-16: the mirror is generated)
- **Major Bump Only for Meaning Changes.** When a JSON schema field's meaning changes (the semantics of the value for consumers), require a major schema-version bump and verify that the reporter, schema documentation, stability contract, and version pins agree. A change that only adds a new cause that maps to an existing verdict, without altering what that verdict means to consumers, does not require a version bump. For example, when a new failure type causes a mutant to receive the existing `summary.errored` verdict, whose meaning remains 'mutants the run could not judge, excluded from the score', do not require a schema bump; only update the documentation naming the new cause. (cubic `d6ab7749`)
- **Mutant ID formula documentation.** When reviewing MutantId documentation, verify that it lists the file path, qualified name, operator, mutated code, and occurrence among identical mutants, and the subject ordinal among same-named subjects, and explains which edits change the ID. (cubic `e6fcc178`, updated 2026-11-16)
- **JSON Output Determinism.** For Mutineer JSON reports, preserve the byte-identical output guarantee when inputs and results are the same, except the run-specific `details` of an errored mutant and the wall-clock values `timing` and each entry's `seconds` (schema `1.11`, #495), and clarify that changed tests or environments can change results. (cubic `a019c5a0`, updated 2026-11-21)
- **Mutineer Exact Threshold Guidance.** When reviewing Mutineer JSON schema guidance for threshold gates, require a positive `summary.killed + summary.survived` denominator and compare counts by cross-multiplication using decimal or rational arithmetic for fractional thresholds. (cubic `7f93da1d`)
- **Baseline Report Compatibility.** When reviewing Mutineer baseline compatibility, preserve support for saved full-run 1.x reports, reject diff-scoped reports with exit 2, and treat JSON schema version separately from the gem release version. (cubic `949c26ec`)
- **Same-File Legacy Baseline Matching.** When diffing against a baseline without `summary.id_format`, match a survivor through its legacy ID only if its file path, normalized with `ProjectPath`, equals the stored survivor's file path. A stored `file` that is absolute and outside the project root (a baseline from another machine) matches on its legacy ID alone. (cubic `47090065`, updated 2026-11-16)
- **Require Full-Scope Baseline Refreshes and Committed PR Baseline.** When a Mutineer workflow creates or refreshes a full baseline and compares PR runs against it, require that `only:` remains unset for both the baseline generation (or refresh) and the PR comparison, and that `baseline:` is removed from `.mutineer.yml` during the baseline generation so the refresh describes the default branch without comparing against the old report. Pass the baseline explicitly on PR commands or the Action input, and verify the full intended scope (fail-fast disabled, no `--only` or `only:` filter) before replacing the saved baseline. Ensure the refreshed baseline is committed at the path the PR gate consumes (`.mutineer/baseline.json`), not merely uploaded as a differently named artifact, and document/verify that the refresh downloads the artifact, checks that `summary.score` is non-null and `no_verdict` is empty, then commits it to that path. (cubic `5bff8164`)
- **Skip Scoped Baseline Score Drops.** When reviewing `--baseline` behavior for runs using `--since`, do not claim that a score drop fails the baseline check; the scoped score has a different denominator. Not when: Do not apply the score-drop exception to new-survivor or incomplete-run checks; the stated exception concerns only score drops under `--since`. (cubic `5e52dd4c`)
- **Match Rails Baseline Refresh to CI.** When reviewing a Rails baseline refresh in `docs/rails.md`, verify that its sources, test files, and operators match the CI gate and that the command preserves the workflow's Rails settings. (cubic `9749887f`)
- **Fixed Means Decided.** In `Baseline#diff` (`lib/mutineer/baseline.rb`) and the `baseline` rows of `docs/json-schema.md`, a stored survivor is in `baseline.fixed_survivors` only when this run killed or ignored it, or when a full run inside the selected sources and operators no longer has it, or when its source file was removed from the project, whatever was selected. Any other current result puts it in `baseline.unverified_survivors` with its status. (#283)
